Scrum vs Kanban

Метод Монте-Карло для сравнительного анализа эффективности Agile-методологий при разработке веб-приложений. Симуляция на сервере (Python / NumPy). Параметры калиброваны по открытым Jira-датасетам (Apache Software Foundation JIRA, GitHub Issues open-source проектов).

Параметры проекта
Источник данных: Открытые Jira-датасеты Apache Software Foundation (JIRA), Mozilla Bugzilla, GitHub Issues open-source проектов. Параметры по умолчанию соответствуют медианным значениям выборки из 12 веб-проектов (n ≈ 4 800 задач).
Общие
Длительность проекта (итераций)ⓘСколько шагов длится виртуальный проект. Один шаг ≈ один спринт (Scrum) или такой же по длине отрезок для Kanban. Календарные дни проекта ≈ число итераций × длительность спринта (дни).12
Размер командыⓘЧисло людей в команде. Используется в подсказках по WIP (закон Литтла) и согласуется с выбранным сценарием.6
Коэффициент неопределённости (σ)ⓘσ — масштаб случайных отклонений (логнормальные шумы вокруг velocity, длительностей и др.). Выше σ — шире разброс метрик между прогонами Монте-Карло.0.30
Scrum
Длительность спринта (дни)ⓘДлина одного спринта в календарных днях (7–31). Задаёт масштаб времени для Scrum и длину одного дискретного шага в модели Kanban.14
Базовая скорость (story points)ⓘОжидаемая «ёмкость» спринта в story points (относительные единицы). В симуляции от неё считается число задач с учётом накладных и случайности.42
Накладные расходы церемоний (%)ⓘДоля времени спринта на Scrum-церемонии (планирование, дейли, ревью, ретро и т.д.), а не на работу по задачам, 1–100%. Чем выше — тем меньше эффективной ёмкости в формуле задач.15
Kanban
WIP-лимит на этапⓘМаксимум задач одновременно на этапе канбан-доски (WIP-лимит). Регулирует параллелизм и очереди в ветке Kanban модели.4
Базовый цикл задачи (дни)ⓘТипичное цикловое время одной задачи для Kanban: значение слайдера делится на 10 (на экране 3.5 соответствует положению 35). Задаёт центр логнормального разброса длительностей.3.5
Интенсивность потока (задач/день)ⓘОжидаемая интенсивность потока задач в день для Kanban (значение слайдера / 10). Влияет на загрузку системы при заданном WIP.2.2
Количество итерацийⓘСколько независимых прогонов Монте-Карло выполнить локально в браузере. Больше прогонов — точнее оценки, дольше счёт.

Когда выбирать Kanban

Непрерывный поток задач

При высокой частоте запросов (> 2 задач/день) Kanban обеспечивает меньшее цикловое время за счёт WIP-лимитов и устранения узких мест.

Высокая неопределённость требований

При σ > 0.40 Kanban превосходит Scrum по cycle time: задачи не «заперты» в спринте и могут быть переприоритизированы немедленно.

Общие рекомендации

Scrumban как гибридный подход

При σ > 0.35 и регулярных релизах рекомендуется Scrumban: фиксированные ревью-точки Scrum + WIP-лимиты Kanban. По результатам симуляции снижает cycle time на 15–22%.

Оптимизация WIP-лимитов

Оптимальный WIP = размер_команды × 0.75–1.0 (закон Литтла). Рассчитывается после запуска симуляции.
